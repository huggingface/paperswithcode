# ADR 0006: Scheduled jobs and CRON health

Status: accepted

Decisions moved out of backend code comments. Each section names the code it governs; update or remove a section when that code changes.

## Below-reserve GitHub budget after a reserve stop is contention, not failure

The hot GitHub trending job checks the remaining rate limit before each call and stops at a reserve. If a later reading is below the reserve after such a stop, another job sharing the same token spent the budget. Health reports this as degraded (shared budget contended) rather than broken, because the reserve mechanism worked.

Code: `backend/services/cron_health.py::_hot_github_trending_contract`

## Benchmark gap review looks back two days for new benchmarks

The benchmark gap review enqueue job runs daily and selects benchmarks created in the last --new-benchmark-days days. The default is two days rather than one so that a single missed or failed daily run does not permanently skip benchmarks created that day. Shortening the window to match the schedule exactly would silently lose boards after any outage.

Code: `backend/scripts/enqueue_benchmark_gap_review.py::main`

## CRON alert state file is world-readable

The CRON failure monitor runs as the pwc-cron user, while the admin dashboard reads its alert state as the web app user. save_state writes to a temp file, chmods it 0644, then atomically replaces the state file, so the dashboard can read it; the default restrictive temp-file mode would hide alerts from the dashboard.

Code: `backend/services/cron_failure_alerts.py::save_state`

## CRON alerts recover only on a successful launcher exit

Failure streaks are computed over a 24-hour window. When an open alert's failures age out of that window without a new success, the alert stays open; a 'recovered' message is posted only when the latest launcher exit succeeded. Otherwise a job that stopped running entirely would be falsely reported as recovered.

Code: `backend/services/cron_failure_alerts.py::plan_alerts`

## CRON scripts exit non-zero when their external dependency is unusable

The admin CRON dashboard shows failures only through the job's exit code. refresh_x_post_likes exits 1 whenever the paid X API fallback errors (bad token, no credits) even if other work succeeded, and warm_paper_suggested_questions exits 1 when every generation failed, which indicates the model is unavailable.

Code: `backend/scripts/refresh_x_post_likes.py::main`, `backend/scripts/warm_paper_suggested_questions.py::main`

## Citation refresh closes its selection transaction before calling Semantic Scholar

The citation refresh CRON selects its papers in one database transaction and closes that session before making any Semantic Scholar request. Holding a transaction open across slow, rate-limited API calls would pin connections and locks on the shared production database.

Code: `backend/tests/paper/test_update_citations_cron.py::test_short_due_selection_is_topped_up_with_early_refreshes`

## Citation refresh prioritises recent papers

Recent papers gain citations fastest and feed paper trending. When Semantic Scholar throttling limits how many papers a refresh run can cover, papers published within RECENT_PAPER_DAYS are refreshed before older ones.

Code: `backend/services/paper_citation_refresh_service.py::PaperCitationRefreshService.pending_chunk`

## Consecutive-failure Slack alerts are counted within a 24-hour window

failure_alert_after posts a Slack alert after that many consecutive failed production runs. Failures are counted from launcher exits in the last 24 hours, so the threshold must be reachable within that window given the job's schedule, or the alert can never fire.

Code: `backend/services/cron_registry.py::CronJobDefinition`

## Coverage-only freshness queries do not report write timestamps

Some CRON outputs live in tables without a write timestamp, so their freshness query can report coverage only. Such jobs set db_freshness_reports_writes=False, and the health evaluator then does not treat a missing last_write as evidence of stale output; the run log is the output proof instead.

Code: `backend/services/cron_registry.py::CronJobDefinition`

## Daily curation failure counts cover only the rolling cohort

The registry SQL for daily curation counts failed and partial workflows only within the rolling cohort that the enqueuer revisits. Because old failures age out, any nonzero count is treated as broken and requiring attention.

Code: `backend/services/cron_health.py::_daily_curation_contract`

## Home-feed enrichment freshness is judged by cohort coverage

When every visible paper is already covered the job writes no row, so write age cannot measure its health. The freshness query instead measures coverage of the home-feed paper cohort.

Code: `backend/services/cron_registry.py`

## Idle event-driven queues are healthy despite stale writes

Some CRON outputs, such as the curation thumbnail queue and the suggested-questions backfill, write nothing when there is no work. Their health contracts treat stale write timestamps as healthy when the queue is empty or coverage is complete, and only judge staleness while work is waiting. Otherwise an idle queue would show as broken.

Code: `backend/services/cron_health.py::_curation_thumbnail_contract`, `backend/services/cron_health.py::_suggested_questions_contract`

## Launcher history keys by dashboard job id, falling back to health_job

Launcher records carry 'job', the dashboard id, and 'health_job', the log file name. For lane jobs these differ (sync_mmeb_v2 logs to 'v2'), so history is keyed by 'job' first and 'health_job' only as a fallback. Keying by health_job would attach lane runs to ids the dashboard does not know.

Code: `backend/services/cron_health.py::fetch_launcher_history`

## Launcher history read is capped at 4 MiB

The CRON health dashboard reads launcher history records with MAX_LAUNCHER_HISTORY_BYTES = 4 MiB. The cap is sized to hold about a day of launcher records at the current every-minute job cadence, matching the 24-hour history window. If job cadence grows, the cap must grow too or the history will silently truncate.

Code: `backend/services/cron_health.py`

## Launcher log terminal records are skipped when finding launches

The persistent launcher log writes a launch record for each run, followed by terminal records carrying an 'event' field such as 'exit' or 'lock_skipped'. fetch_persistent_execution skips records with an event so that only launch records are matched to jobs.

Code: `backend/services/cron_health.py::fetch_persistent_execution`

## Lock skips count as missed work for laned CRON jobs

Most CRON jobs treat a run skipped because the launcher lock was held as a harmless overlap. Jobs whose runs differ in their work, such as thumbnail preload lanes, set lock_skip_misses_work so a lock-skipped run is reported as missed work, since each lane overrunning its own next slot leaves its share undone.

Code: `backend/services/cron_registry.py::CronJobDefinition`

## Lock stale flag requires a confirmed held lock

get_lock_state keeps the backward-compatible 'stale' field for existing consumers, but it is true only when the lock probe confirms the lock is held and its age exceeds the expected runtime. A lock file whose hold state is unknown or free is never reported stale, so leftover lock inodes do not raise false alarms.

Code: `backend/services/cron_health.py::get_lock_state`

## Model release radar is judged by exit status only

The model release radar writes its JSON to the journal and turns unindexed releases into queued resolution jobs, so it has no table write to check. The script exits 1 only when every source failed, so a clean exit proves the scan and the job uses the report_only output evaluator.

Code: `backend/services/cron_registry.py`

## Only a currently held kernel lock blocks a job

Lock file inodes can persist indefinitely, so their existence is not evidence of a blocked job; only a lock currently held in the kernel counts. A held lock without a running job is called a broken orphan only after one minute, giving the wrapper a short handoff window between acquiring the lock and starting the unit.

Code: `backend/services/cron_health.py::evaluate_job_health`

## Provider throttling degrades health only above 5% of calls

Jobs retry throttled provider requests, so a few throttled calls are routine. Health marks a job degraded for throttling only when throttled requests are at least 5% of API calls (or when no call count is reported). Flagging any throttling would make the dashboard noisy without signalling real trouble.

Code: `backend/services/cron_health.py::_provider_counter_contract`

## Research digest freshness is judged by weekly window coverage

Research digests are written once a week in a Monday 08:00 UTC window while the job runs hourly, so write age would look stale most of the week. The freshness query instead checks coverage of the current weekly window. It returns aggregates only and never exposes recipients or payloads.

Code: `backend/services/cron_registry.py`

## Research digest window is missing only after a two-hour grace

Research digests are sent by an 08:00 run. Health reports this week's window as missing only after 120 minutes and only when the previous week had digests, because no followers means legitimately no digests. This avoids false alarms while the run is in progress or when nobody follows topics.

Code: `backend/services/cron_health.py::_research_digests_contract`

## Running jobs take the newest start time, not the log's last run

A queued or just-started invocation has not written to its log yet, so the log's last_run still refers to the previous run. When a job is running, health uses the newest of the available start timestamps to compute its age, so a fresh run is not judged by the previous run's start.

Code: `backend/services/cron_health.py::evaluate_job_health`

## Timer activation, not restarts, excuses a missed first slot

Service restarts and reboots move a timer's ActiveEnterTimestamp, but with Persistent=true systemd keeps LastTriggerUSec, so only a timer that has never fired can be considered installed after the expected slot. The health check excuses a missed slot only in that case. Manual runs before activation leave completion evidence but do not owe a timer slot.

Code: `backend/services/cron_health.py::_execution_health`

## Trending units must not order After= the GitHub stars service

update_github_stars runs close to its full hourly interval and re-fires under Persistent=, so a systemd After= edge from a trending unit onto pwc-cron-update-github-stars.service keeps the trending jobs waiting indefinitely and starves the whole trending chain. Trending service units must not reference the stars service.

Code: `backend/tests/cron/test_schedule_units.py::test_trending_units_never_wait_on_the_hourly_stars_service`

## URL extraction agent is stale only after a week

The URL extraction agent runs on manual dispatch, roughly weekly, not on an hourly timer. Its stale_after_minutes is seven days so the health dashboard does not flag it between dispatches.

Code: `backend/services/cron_registry.py`

## URL extraction freshness uses rows it created, not papers.updated_at

papers.updated_at changes on every catalog edit, so it cannot show that the URL extraction agent ran. Its freshness query reads created_at from repositories and project pages with source='ai_extraction', which only that agent writes.

Code: `backend/services/cron_registry.py`

## Workflow status refreshes runs that fell off the recent-run page

A GitHub Actions rerun updates the original run in place rather than creating a new run. If an old failed run has fallen outside the repository-wide recent-runs page, the dashboard re-fetches that workflow instead of retaining the cached failure, so a successful rerun clears the alarm.

Code: `backend/services/cron_health.py::fetch_workflow_statuses`
